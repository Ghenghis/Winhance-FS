Agent Systems — Comparison & Recommendation

Date: 2026-05-13 Scope: Hermes vs CLI agents for Winhance-FS Project: Windows · .NET 8 · WPF · Rust · Python

TL;DR & Verdict

⚡ Recommendation (updated post-leak, May 2026)

Go with the open-source CLI route, not Hermes, not proprietary Claude Code. Hermes Agent has no native Windows support (WSL2 only) — a deal-breaker for a Win32 / WPF / .NET 8 codebase. Proprietary Claude Code is still excellent quality, but the March 31 2026 source leak spawned a generation of MIT-licensed forks that give you the same architecture without the vendor lock or the Anthropic-only OAuth.

Build a backend-switchable OSS CLI stack — each runnable inside its own Docker Sandbox (microVM):

  1. OpenCode — primary driver, MIT, ~120k★, multi-provider, replaces proprietary Claude Code
  2. Crush — Go-based TUI from Charm; fastest interactive feel
  3. Goose — free open-source, BYO-model, 25+ provider support (Block, Apache 2.0)
  4. OpenHands CLI — open multi-step autonomy (68k★, model-agnostic)
  5. Kilo Code — multi-mode orchestrator with worktree-isolated parallel agents

Bench reserves: Claw Code (Python port of leaked source, useful as reference), Cline (VS Code companion), Aider (architect-mode surgical edits), Codex CLI (if OpenAI quota is sunk cost), proprietary Claude Code (only when peak quality is worth the lock-in).

Isolation: Docker Sandboxes (microVM, ~125 ms boot) — supports all of them. Switching is a launcher flag, not a rebuild.

QuestionAnswer

Is the CLI route better?YES — native Windows, multi-LLM, container-isolated per agent.

Why the CLI Route Wins for This Project

  • Native Win32 access. Registry tweaks, WPF bring-up, WIM mount, PowerShell — all need Windows. Hermes loses here by design.
  • Backend interchangeability. Each CLI exposes the same conceptual surface (read file, run command, edit file, commit). Behind a launcher, they become drop-in interchangeable.
  • Cost shaping. Free local-model runs (Goose + Ollama) for bulk reading; premium Claude/GPT for hard reasoning. Same project, different backend per task.
  • Failure recovery. When provider A is rate-limited, the launcher rotates to B. Hermes binds you to a single agent loop.
  • Already proven here. This shift's 5-agent parallel audit used the same pattern — independent CLI agents, one shared worktree, divergent prompts.

The CLI stack is not a downgrade from Hermes — it is a superset. Run Hermes inside one of the CLI sandboxes if you want its memory + skills, but don't force the whole project to live inside Hermes.

Final Recommendation

Adopt the 5-CLI backend-switchable stack with Docker Sandbox microVMs.

Keep Claude Code as the daily driver. Wire the other four as alternate backends behind a single launcher. Each launches into its own microVM with the worktree bind-mounted read-write and the project's MCP servers reachable on the host. Switching backends is one flag — the agent never sees the other backends, but you do.

Hermes Agent stays on the shelf. Re-evaluate if Nous ships native Windows support or if the project ever sprouts a Linux-side ops component (server-side WSL/SaaS, etc.).
