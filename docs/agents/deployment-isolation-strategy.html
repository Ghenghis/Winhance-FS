Deployment & Isolation Strategy

Goal: Seamless backend switching with microVM isolation Tools: Docker Sandboxes (Firecracker) / Hyper-V / WSL2 Host: Windows 11 + Docker Desktop 4.40+

Why Isolate Agents at All

A coding agent running with your shell privileges can read every file you can read, write anywhere you can write, exfil any token in your environment, and shell out to anything on PATH. For Winhance-FS specifically, the project has registry-write paths, WIM mount tooling, and privileged PowerShell scripts. An agent misfire on the host is more painful than an agent misfire in a microVM.

  • Blast radius cap. Sandbox = a wrong rm -rf deletes the sandbox, not %USERPROFILE%.
  • Token containment. API keys live in the VM, not exported globally. One leaked key has one revocable scope.
  • Reproducible env. Every agent gets the same .NET SDK, same PowerShell, same MCP servers. No "works on my machine".
  • Parallel safety. Five agents fighting over the same git index is a merge nightmare; five microVMs each on their own worktree is just five PRs.
  • Backend swap with no host pollution. Removing Goose is docker rm, not "uninstall npm package and pray".

Isolation Levels — Pick Your Strength

LevelBoundaryOverheadBootRecommended For
Bare host None — agent runs as you 0% instant Quick interactive Claude Code sessions on trusted code only
Docker container Shared kernel; namespaces + cgroups ~2-5% < 1s OpenHands default runtime; Goose; Codex on trusted prompts
gVisor User-space syscall filter 10-30% I/O ~1s Mid-trust autonomous loops
Firecracker microVM Dedicated kernel + virtio ~5 MiB + small CPU ~125 ms Default for Winhance — Docker Sandboxes
Hyper-V VM Full hypervisor Higher seconds When you need Windows guest inside (rare for agents)
WSL2 distro Lightweight hypervisor Low ~1-2s Hermes Agent (if you keep it on the bench)
Pick: Docker Sandboxes (Firecracker microVM) for all five CLI backends. It is the only option that (a) supports Claude Code / Codex / Gemini / OpenHands / Goose out of the box, (b) boots in ~125 ms, and (c) gives each agent its own kernel without Hyper-V overhead.

The MCP servers live on the host and the microVM dials them via host.docker.internal. That keeps one canonical project index, even though five different VMs may be querying it.

Base Image — One Build, Five Personalities

# .agents/sandbox/Dockerfile.base
FROM mcr.microsoft.com/dotnet/sdk:8.0-jammy AS base

# System tools the agents expect to find on PATH
RUN apt-get update && apt-get install -y --no-install-recommends \
      curl wget git gh unzip ca-certificates \
      python3 python3-pip python3-venv \
      powershell \
    && rm -rf /var/lib/apt/lists/*

# Node 22 (for npm-distributed CLIs: Claude Code, Codex, Kilo)
RUN curl -fsSL https://deb.nodesource.com/setup_22.x | bash - \
    && apt-get install -y nodejs

# uv (for OpenHands Python install)
RUN curl -LsSf https://astral.sh/uv/install.sh | sh \
    && ln -s /root/.local/bin/uv /usr/local/bin/uv

# Working directory + standard mounts
WORKDIR /repo
VOLUME ["/repo", "/agent"]

ENTRYPOINT ["/agent/entrypoint.sh"]
Build once: docker build -t winhance-agent-base:1.0 -f Dockerfile.base .
Every agent flavor extends this in a one-line per-agent Dockerfile (next section).

Build all five at once:

cd C:\Winhance-FS-Repo\.agents\sandbox
docker build -t winhance-agent-base:1.0   -f Dockerfile.base .
foreach ($flavor in "claude","codex","goose","openhands","kilo") {
  docker build -t "winhance-agent:$flavor" -f "Dockerfile.$flavor" .
}

Docker Sandbox Launcher

# .agents/launcher/docker-sandbox.ps1
param(
  [ValidateSet("Claude","Codex","Goose","OpenHands","Kilo")]
  [string]$Backend = "Claude",
  [string]$Task,
  [switch]$ReadOnly,
  [switch]$Worktree,
  [string]$WorktreeName = "agent-$($Backend.ToLower())-$(Get-Random -Maximum 9999)"
)

$repo   = "C:\Winhance-FS-Repo"
$image  = "winhance-agent:$($Backend.ToLower())"
$mount  = if ($ReadOnly) { "$repo:/repo:ro" } else { "$repo:/repo" }

if ($Worktree) {
  git -C $repo worktree add "$repo\.claude\worktrees\$WorktreeName" -b "agent/$WorktreeName"
  $mount = "$repo\.claude\worktrees\$WorktreeName:/repo"
}

docker run --rm -it `
  --runtime=sandbox `  # Docker Sandboxes microVM runtime
  --network=bridge `
  --memory=4g --cpus=2 `
  -e ANTHROPIC_API_KEY=$env:ANTHROPIC_API_KEY `
  -e OPENAI_API_KEY=$env:OPENAI_API_KEY `
  -e GOOGLE_API_KEY=$env:GOOGLE_API_KEY `
  -e MCP_HOST=host.docker.internal `
  -v $mount `
  -v "$repo\.agents\$($Backend.ToLower()):/agent:ro" `
  -v "$repo\.agents\shared:/agent/shared:ro" `
  $image $Task

Usage

# One-shot in a microVM:
.\.agents\launcher\docker-sandbox.ps1 -Backend Goose -Task "./recipes/warning-sweep.yaml"

# Read-only audit run:
.\.agents\launcher\docker-sandbox.ps1 -Backend Claude -Task "audit src/Winhance.WPF" -ReadOnly

# Parallel fan-out, each agent gets its own worktree:
1..4 | ForEach-Object -Parallel {
  .\.agents\launcher\docker-sandbox.ps1 -Backend Kilo -Worktree `
    -Task "close audit finding P$_"
} -ThrottleLimit 4

Bind Mounts & State Surface

MountModePurposePer-agent?
/reporw (or ro)The codebase. Bind from main worktree or per-agent worktree.Configurable
/agentro.agents/<backend>/ — config & recipes for the chosen CLI.Yes
/agent/sharedro.agents/shared/ — MCP config, AGENTS.md import, routing.No (shared)
/cacherwNamed volume for npm/uv/dotnet caches; survives container lifecycle.Shared
/staterwOptional: agent's own conversation/skills DB (for Hermes-style memory).Yes
Do NOT mount: %USERPROFILE%, %APPDATA%, SSH keys, the docker socket, the host registry hive. The agent gets exactly what it needs and nothing else.

MCP Bridge — One Server Pool, N Clients

Each CLI's config (Claude's settings.json, Goose's config.yaml, etc.) points at http://host.docker.internal:<port> for MCP servers. On the host you run them once as a Windows service or a long-lived terminal: 

# .agents/shared/start-mcp-pool.ps1
Start-Process npx -ArgumentList "-y","@modelcontextprotocol/server-filesystem","C:\Winhance-FS-Repo"
Start-Process npx -ArgumentList "-y","@modelcontextprotocol/server-sequential-thinking"
Start-Process node -ArgumentList ".agents/shared/project-mcp/index.js"

Tip: run the MCP pool inside its own microVM if you want full isolation — then the agents dial that VM's hostname instead of the host. Five agents, one MCP brain.

Seamless Switching — How a User Actually Swaps Backends

  1. The user runs winhance-agent -Backend Goose -Task "..." from the same terminal session.
  2. The launcher resolves Goose → image winhance-agent:goose.
  3. Docker spins up a fresh microVM in ~125 ms (Firecracker boot).
  4. The repo bind-mount means the agent immediately sees current files, current branch, current uncommitted changes.
  5. The shared AGENTS.md and MCP pool mean it inherits the project context — no re-briefing.
  6. On exit, the VM is destroyed. Side effects landed on disk via the bind-mount; nothing else persists.
What "seamless" buys you: A 3-step flow (switch flag → boot → mount) takes well under one second per swap. There is no install dance, no PATH reshuffle, no API-key juggling. The user's mental model is "I'm picking a different brain for the same project."

Parallel Fan-Out — N Agents at Once

The "20 agents" pattern works because each VM gets its own worktree and its own merge target.

     ┌─────────────────────────────────────┐
     │   Kilo Orchestrator (host VM)       │
     │   Splits task → 4 subtasks          │
     └────────────┬────────────────────────┘
                  │ fan-out
   ┌──────────────┼──────────────┬──────────────┐
   ▼              ▼              ▼              ▼
┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
│Worktree│   │Worktree│   │Worktree│   │Worktree│
│  + VM  │   │  + VM  │   │  + VM  │   │  + VM  │
│ Claude │   │ Codex  │   │ Goose  │   │OpenHnds│
└────┬───┘   └────┬───┘   └────┬───┘   └────┬───┘
     │             │              │              │
     └─────────────┴───────┬──────┴──────────────┘
                           ▼
                  4 branches → 4 PRs → human review
                           ▼
                   merge winners; close losers
  • Worktree per agent: git worktree add creates an independent checkout. No fights over index lock.
  • Branch per agent: Each VM commits to agent/<name>. PRs target main, reviewed independently.
  • Throttle limit: PowerShell's -ThrottleLimit caps concurrency. 4-8 simultaneous VMs is comfortable on 32 GB / 8 cores.
  • Mixed backends OK: the four agents above are different CLIs — useful for getting independent opinions on the same problem.

Cost & Quota Strategy

Codex CLIIncluded with ChatGPT Plus/Pro subscription tierTest fix loops; autonomous batch runs

OpenHandsWhatever your BYOK model costsOvernight autonomous loops on cheaper models
Kilo CodeBYO providers; tool itself freeMulti-mode work; mode picks the cheapest model for the role
Routing rule of thumb: when in doubt, send the task to Goose+Ollama first. If the local model produces something reasonable, accept it. If it doesn't, escalate the same prompt to Claude. You'll cut spend by 60-80% on routine work without hurting hard-task quality.

Observability — Know What the Agents Did

  • Per-VM transcript: redirect each session's stdout into .agents\logs\<backend>-<timestamp>.log.
  • Git diff is the audit log: every action a sandboxed agent takes appears as a commit. Use git log --author="agent/*" to filter.
  • Token spend dashboard: each CLI emits cost telemetry — pipe to a shared .agents\state\spend.jsonl via a hook.
  • Sandbox metrics: docker stats shows live CPU/memory per agent VM.
  • Tail multiple agents at once: Get-Content -Wait .agents\logs\*.log in a side terminal.

Security Posture

ConcernMitigation
API key leakKeys are env-injected into the microVM only; never written to disk inside it.
Prompt injection from project filesAGENTS.md sets explicit allow/deny; bind mounts are scoped to the repo only.
Agent runs rm -rf /It removes the VM's rootfs, not your host. docker rm recreates.
Agent commits secretsPre-commit hook scans for secrets; lives in the bind-mounted repo so all agents are subject to it.
Agent escalates inside VMVM kernel is fresh per launch; no persistent state to escalate against.
Network exfilIf paranoid: run microVMs on a separate Docker network with only host.docker.internal + LLM endpoints reachable.

Summary

What this gives Winhance-FS:
  • Five high-quality CLI agents, each behind a microVM boundary.
  • One launcher flag (-Backend X) switches between them with no install / uninstall churn.
  • Shared MCP & AGENTS.md mean every agent starts from the same project understanding.
  • Per-agent worktrees enable safe parallel fan-out without merge chaos.
  • Hermes Agent stays on the bench — pick it up only if a Linux-side ops surface materializes.

Next step is a 1-day spike: build the base image and the launcher with two backends (Claude + Goose), run one P0 fix through each, measure walltime and token cost. If both pass, expand to the full five.
